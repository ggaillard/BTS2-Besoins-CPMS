# Grille d'évaluation

Chaque jalon est évalué sur les artefacts présents **dans le dépôt** à la date du jalon (dernier commit pris en compte) et, pour J2 et J4, sur une présentation orale.

## Répartition

| Jalon | Ce qui est évalué | Poids |
|---|---|---|
| **J1 — Besoin validé** | C1, C2, C3 (au moins 3 entretiens), M1 §1, S1 §1, P3 | 20 % |
| **J2 — Go / No-go** | C4, C5, M1 §2, S1 §2, S2, P2 + présentation de 10 min au client | 30 % |
| **J3 — Plan validé** | C6, P1, P4, M2, S3 | 25 % |
| **J4 — Bilan** | M3, P3 clôturé, P2 à jour + présentation de 10 min | 15 % |
| **Tout au long** | Usage de GitHub (tickets, jalons, commits), tenue des rôles, comportement en entretien | 10 % |

## Critères par verbe

Chaque critère est noté **0** absent · **1** insuffisant · **2** attendu · **3** remarquable.

### Concevoir
| Critère | 0-3 |
|---|---|
| Les entretiens sont préparés, menés avec des questions ouvertes, et restitués en séparant faits et interprétations | |
| Le besoin réel est distingué de la solution demandée ; l'énoncé du besoin ne nomme aucune technologie | |
| Les récits utilisateur sont testables (critères Gherkin) et priorisés de façon crédible | |
| Au moins trois scénarios, dont un sans développement, sont comparés objectivement (TELOS, sources) | |
| La recommandation découle de l'analyse ; le « No-go » est accepté s'il est argumenté | |
| La solution retenue est décrite de façon exploitable (maquettes, architecture, décisions justifiées) | |

### Piloter
| Critère | 0-3 |
|---|---|
| Le plan de projet est réaliste : charges chiffrées, jalons datés, RACI cohérent, budget relié à C5 | |
| Les risques projet sont formulés, cotés, et suivis (mise à jour visible dans l'historique Git) | |
| Le déploiement prend en compte les utilisateurs réels (accompagnement, communication, retour arrière) | |
| Le journal de bord est tenu à chaque séance ; les décisions sont tracées | |

### Mesurer
| Critère | 0-3 |
|---|---|
| La situation de départ est chiffrée à partir des documents et des entretiens (calculs vérifiables) | |
| Les indicateurs sont SMART, avec au moins un indicateur d'usage et un indicateur d'effet | |
| Le cahier de recette couvre tous les « Must » et comporte des tests de sécurité | |
| Le bilan compare prévu et obtenu, explique les écarts et en tire des actions | |

### Sécuriser
| Critère | 0-3 |
|---|---|
| Toutes les données manipulées sont inventoriées et cotées DICP avec des justifications concrètes | |
| La fiche RGPD est juste : base légale, minimisation effective, durées, conclusion AIPD argumentée | |
| Les menaces sont propres au cas ; chaque menace a une mesure, dont des mesures organisationnelles | |
| Sauvegarde, continuité et réversibilité sont traitées ; les risques résiduels sont acceptés par le client | |

## Oral (J2 et J4)

| Critère | 0-3 |
|---|---|
| Le discours est adapté à l'interlocuteur (pas de jargon technique non expliqué devant un non-informaticien) | |
| Les chiffres présentés sont sourcés et justes | |
| L'équipe répond aux objections du client sans se braquer ni céder sur l'essentiel | |
| Chaque membre intervient et maîtrise l'ensemble du dossier | |

| Bloc | Compétence | Artefacts qui en apportent la preuve |
|---|---|---|
| Bloc 1 | Répondre aux incidents et aux demandes d'assistance et d'évolution | C3, C4 |

| Bloc 2 SLAM | Concevoir et développer une solution applicative | C4, C6 |
